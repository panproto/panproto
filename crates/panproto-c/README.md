# panproto-c

[![MIT](https://img.shields.io/badge/license-MIT-blue.svg)](../../LICENSE)

C ABI for panproto. The foundation for non-Rust language bindings whose host runtime cannot tolerate Rust panics propagating across the FFI boundary, GHC's RTS being the immediate motivating case.

## What it does

This crate exposes panproto's core operations behind a `safer-ffi`-generated C ABI. Two wire formats coexist at the boundary: opaque `u32` handles into a thread-local slab on the hot path (no serialization), and CBOR via `ciborium` on the cold path (protocol ingest, error envelopes, schema introspection). Every entry point is wrapped in `std::panic::catch_unwind`; panics convert to a CBOR-encoded error envelope retrievable via `pp_last_error_take` rather than aborting the host process. The release profile uses `panic = "unwind"`.

Compiled as both `cdylib` and `staticlib`; downstream consumers (currently the Haskell binding under `bindings/haskell/`) link against the static archive to avoid runtime symbol resolution. A C header (`include/panproto.h`) is generated by the `headers` cabal feature and committed in-tree so consumers get a stable IDL.

The vertical slice released in `0.41.0` exposes `pp_init`, `pp_handle_free`, `pp_buf_free`, `pp_last_error_take`, `pp_protocol_define`, and `pp_protocol_serialize`. Schema, lens, migration, instance, expression, and VCS surfaces land in subsequent releases as the corresponding capability classes lift on the Haskell side.

## Building

From the workspace root:

```sh
cargo build -p panproto-c --release
```

This produces `target/release/libpanproto_c.{a,so,dylib,lib}`. To regenerate the C header after adding new `#[ffi_export]` entry points:

```sh
cargo test -p panproto-c --features headers --test headers -- --ignored
```

The header is committed at `crates/panproto-c/include/panproto.h`. CI rejects diffs.

## Architectural decisions

- **`safer-ffi` over `cbindgen`**: compile-time `ReprC` layout guarantees catch struct-mismatch bugs at build time rather than at runtime when the host reads garbage.
- **Hot/cold wire-format split**: a handle API is mostly `u32 -> u32`; serializing every call is waste. CBOR is reserved for the schema-shaped payloads where structural equivalence with `serde`-defined Rust types matters.
- **No tokio runtime**: every entry point is sync. If async work is needed internally, a current-thread runtime is spun up per call. This avoids the GHC-RTS deadlock class that bit `pydantic-core` and similar projects.
- **Thread-local slab allocator**: mirrors `crates/panproto-wasm/src/slab.rs`. Slot reuse on free; double-free is a no-op.
- **Panic-to-status conversion**: `extern "C"` + Rust panic is undefined behavior. Every entry point goes through `panic::guard`, which catches unwinds, stashes a CBOR error envelope in a thread-local, and returns `PpStatus::Panic`.

## Status codes

Mirrors `panproto_c::error::PpStatus`:

| Code | Variant | Meaning |
|------|---------|---------|
| 0 | `Ok` | Success. |
| 1 | `Err` | Generic failure; details in the last-error envelope. |
| 2 | `Panic` | A Rust panic was caught at the FFI boundary. |
| 3 | `InvalidHandle` | Handle does not refer to a live slab slot. |
| 4 | `TypeMismatch` | Handle resolves but the underlying resource is the wrong kind. |
| 5 | `Serialization` | CBOR encode or decode failed. |
| 6 | `Internal` | Other failure from `panproto-core`. |

Numeric values are part of the C ABI contract; never reorder.

## Distribution

Hackage forbids precompiled binaries, so the Haskell binding fetches per-platform `panproto-c` artifacts from the GitHub Release rather than building from source. The `.github/workflows/build-panproto-c-bindist.yml` workflow builds `libpanproto_c.{a,so,dylib,lib}` on tag for Linux x86_64/aarch64, macOS arm64+x86_64, and Windows x86_64-msvc, and uploads them as release assets. Linux uses `cargo-zigbuild` so the static archive does not collide with GHC's RTS on `pthread`/`compiler_builtins` symbols.
