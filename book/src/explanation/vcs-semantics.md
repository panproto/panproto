# Schema version control semantics

`panproto-vcs` stores immutable schema-related objects in a content-addressed directed acyclic graph (DAG). Mutable branch and tag references point into that graph. Its command vocabulary includes familiar operations such as `init`, `add`, `commit`, `branch`, `merge`, `log`, and `diff`, but the stored objects and merge algorithm operate on parsed schema structure rather than lines of source text.

This distinction changes the form of a conflict. A text merge reports overlapping edits to lines. A schema merge compares vertices, edges, constraints, and the other fields of the common representation, then reports incompatible structural edits as typed conflict values. Syntax and protocol validation still run separately; structural merge alone does not guarantee that every merged schema is valid.

## Objects and references

A repository records the format it was written in. `Repository::init` writes `.panproto/format`, holding the repository format version ([`REPOSITORY_FORMAT_VERSION`](https://docs.rs/panproto-vcs/latest/panproto_vcs/constant.REPOSITORY_FORMAT_VERSION.html), currently 1) as a decimal numeral and a line feed, and refuses with `AlreadyARepository` where `.panproto/` already exists. `Repository::open` refuses any other marker content with `UnsupportedRepositoryFormat`, before any object is decoded. A repository with no marker was written before the marker existed, in the only format there has been, so it is read as version 1; reads leave it as it is, and the first write through the store writes the marker. Version 1 is the layout described here, with objects encoded as MessagePack.

Every object identifier is a BLAKE3 digest of the object's type-specific canonical serialization. Objects are stored under `.panproto/objects/`, branch references under `.panproto/refs/heads/`, and tag references under `.panproto/refs/tags/`. The filesystem store writes objects and refs through a flushed sibling temporary file followed by a same-directory rename. It recomputes an object's identifier when reading it and returns `ObjectCorrupted` if the stored object does not match its path. Ref names must consist only of ordinary relative path components.

| Object | Contents |
|---|---|
| `FileSchema`, `SchemaTree`, `FlatSchema` | Per-file schema content, a tree root used by commits, and a flattened migration endpoint. |
| `Migration` | A map between identified source and target schemas. |
| `Complement`, `CstComplement` | Saved data for inverse migration and concrete-syntax reconstruction. |
| `DataSet` | An instance associated with a particular schema: a sequence of trees, one table instance or one graph instance. |
| `EditLog` | A sequence of tree edits, table deltas or graph deltas made against a data set. |
| `Protocol`, `Theory`, `TheoryMorphism`, `Expr` | Protocol and transformation metadata referenced by other objects. |
| `Commit` | A `SchemaTree` root, parent commits, protocol and author metadata, and identifiers for associated migrations, data, complements, edit logs, theories, and renames. |
| `Tag` | An annotated reference to another stored object. |

A data set, complement or edit log records the payload encoding of its bytes: the shape of instance they belong to (tree, table or graph) and the version of that shape's encoding. Version 1 of each is MessagePack of the shape's value, and the table and graph encodings are canonical, so a table or graph object's identifier is a function of the value it holds. An object records the field only when its encoding is not version 1 of the tree encoding, which is the encoding every tree object written before the field existed holds; such an object keeps its bytes, its identifier and its meaning, and version 1 of the repository format holds all three shapes. Decoding refuses an encoding version this build does not read with `UnsupportedPayloadEncoding`, bytes that do not decode whole, or a count they contradict, with `UndecodablePayload`, and a table or graph payload that is not canonical with `NonCanonicalPayload`. [Instance version control](../correctness/instance-version-control.md) states these behaviours as laws.

Garbage collection deletes exactly the stored objects that no root reaches. The roots are the commit `HEAD` resolves to, the target of every ref under `refs/` (branches, tags, remote-tracking refs, the stash and any other namespace), every entry of the stash's reflog, and, when collection runs through the repository, every object the staging index names. Every reference field of every object kind is followed, so collection never removes an object reachable from a ref.

A branch is a mutable reference rather than an immutable object. A commit may have more than one parent, so the commit relation forms a DAG rather than a simple sequence.

## Migration selection at stage

Staging a schema selects the migration the commit will record. The first commit records none. Every later stage diffs the staged schema against HEAD's, refuses an empty diff with `ValidationFailed` and the reason `no changes detected`, and derives a migration with [`derive_migration`](https://docs.rs/panproto-vcs/latest/panproto_vcs/auto_mig/fn.derive_migration.html): the identity on every vertex the two schemas share (a vertex whose kind changed included), the identity on every edge they share, and for an edge whose endpoints survive but which is gone, the edge of the same name between the same endpoints when there is one. When the change both removes a vertex and adds another, the migration may instead take the right leg of an injective span search, pinned by detected renames, when that leg maps more vertices and type-checks; the search pins every vertex of unchanged kind that survives to itself, and a survivor whose kind changed may be sent to a vertex of its old kind. The selected migration is stored as a `Migration` object whose source and target are the identifiers of the HEAD schema and the staged schema stored as `FlatSchema` objects, which is how the migration's identity is tied to the two schemas it relates. [Schema merge](../correctness/schema-merge.md#L-schema-merge-3) states this as a law.

## Validation at stage and commit

Migration validation checks that mapped vertex and edge identifiers exist at both endpoints and that each mapped edge lands between the images of its source endpoints. The same structural obligation is checked during migration compilation, where a failure is reported as `NotAMorphism`. By default, migration errors make staged content invalid and block commit with `VcsError::ValidationFailed`.

Verification can be bypassed deliberately at two points, and both have to be taken for unverified material to reach a commit. `AddOptions::skip_verify` and `AddDataOptions::skip_verify` permit an object to remain pending at stage time; a default commit then refuses it, because "not checked" and "checked and passed" are different states and only the second is a pass. `CommitOptions::skip_verify` is what accepts a pending or invalid stage, and the resulting commit records on its `unverified` field what it accepted, so the bypass is legible in the history rather than only at the moment it was taken. These options weaken the repository invariant and should be treated as explicit overrides rather than ordinary workflow.

When a registered protocol theory contains equations, model validation checks the supplied finite model against them. The evaluator considers at most 10,000 variable assignments for an equation; exceeding that bound returns `ModelCheckLimitExceeded` instead of accepting the equation. If no theory is registered, validation records an advisory that no equations were checked while retaining the available structural checks. `ThWType`, used as an instance theory by several protocol groups, contains two equations connecting arc endpoints to schema-edge endpoints. The schema theory and instance theory remain separate, so the presence of those equations does not mean that `panproto_schema::validate` evaluates them over a `Schema`.

## Structural three-way merge

Let $B$ be a common base and $O$ and $T$ the schemas on the two branches. The categorical account reads merge as a pushout of the divergent changes over their base [@mimramdigiusto2013categorical]:

$$
\begin{CD}
 B @>>> O \\
 @VVV @VVV \\
 T @>>> M.
\end{CD}
$$

The implementation constructs $M$ with a field-by-field structural three-way merge. Compatible additions and modifications are combined. Incompatible edits become `MergeConflict` variants, and conflicted elements retain their base values until the caller supplies a resolution. `apply_resolutions` requires a choice of ours or theirs for every reported conflict and then verifies the resulting square.

For vertices and edges the rule is per element: a value both branches agree on is taken, a branch that left the base value gives way to the other, and three different values are a conflict. Deleting a vertex depends on the other branch's changes at it. When one branch deletes a vertex and the other changes its kind, or adds an edge at it, the merge reports `DeleteModifyVertex` and keeps the vertex with its base kind, so the added edge keeps its endpoint; a merge without conflicts is therefore a well-formed schema. Resolving that conflict takes the chosen side's vertex together with its edges at the vertex. Conflicts are listed sorted by the derived order of `MergeConflict` (by class, then by the contested element), so a conflict's index, which a `ResolutionStrategy` keys on, is the same in every process. [Schema merge](../correctness/schema-merge.md) states these rules as laws and checks them against a reference.

Combining compatible additions means that two branches adding the same name compatibly contribute one element rather than one each, so $M$ is the pushout quotiented by same-name identification. `MergeResult::identified_additions` reports every name collapsed this way. [Pushouts and merge](./semantics/pushouts-and-merge.md) states what that quotient costs.

The routine `verify_pushout` checks the generated cocone: both branch vertex maps must be total, every merged vertex must come from a branch, surviving base vertices must remain present, and the two paths from the base must agree on mapped vertices and mapped base edges. A failure returns `VcsError::PushoutVerification`. This is a cocone check, not a complete runtime proof of the universal property.

`verify_pushout_universal` provides an additional on-demand check against a caller-supplied alternative cocone. It constructs and checks a mediator on vertices. The current API does not establish edge-level factorization, and ordinary merge does not call this verifier. [Pushouts and merge](./semantics/pushouts-and-merge.md) states the distinction formally.

Merge also computes a pullback of theory presentations derived from the base-to-branch diffs. The resulting `PullbackOverlap` is diagnostic metadata in `MergeResult`; the field-by-field merge does not use it to decide whether additions are identical or conflicting. If pullback construction fails, the result stores a `pullback_error` and the CLI reports it. The failure is not interpreted as an empty overlap.

## Data associated with history

Commits may reference data sets and migration complements. A committed merge merges, key by key, the instances its two parents track against those their merge base tracks (`instance_merge::merge_tracked`). A key one side left as the base had it takes the other side's data set; a key both sides changed is merged by deltas: each side's instance is diffed against the base's, and the two deltas merge when they are independent in the sense of [L-edits-1](../correctness/edits.md#L-edits-1), which is the patch-theoretic reading of merge as a pushout of commuting changes [@mimramdigiusto2013categorical]. Sequences of trees merge record by record. Dependent deltas, a merged instance that fails validation, and the cases a delta merge does not cover (a key added on both sides with no common base, a key removed on one side and changed on the other, mixed shapes or schemas) are reported as typed `InstanceConflict` values in a fixed order, and nothing is recorded until each is resolved by choosing a side for its key (`MergeOptions::instance_resolutions`). The merge commit records one data set per key it tracks, lifting tree data recorded against a parent's schema to the merged schema and recording the fresh complements, and stops tracking the keys our parent tracked that the merge drops. [L-instance-version-control-6](../correctness/instance-version-control.md#L-instance-version-control-6) states the merge exactly. Rebase and cherry-pick lift the replayed commit's data and call `verify_square`, then replay the instances the commit changes onto the tip: each changed key's delta is rebased over the delta committed since the commit's parent and applied to the tip's instance, a dependent change refuses the replay with its conflicts, and a clean replay gives what the three-way merge would ([L-instance-version-control-7](../correctness/instance-version-control.md#L-instance-version-control-7)). Despite its name, that function checks one necessary condition: it migrates the lifted data backward through the saved complement and requires recovery of the original data. This is GetPut for the vertical migration, or the square condition with an identity horizontal edge. It does not compare the two paths around a general data-migration square. These operations follow the schema-evolution account of migrations connected by lenses in Cambria [@littvanhardenberghenry2020cambria; @littvanhardenberghenry2021cambria].

Ordinary commit records data that was staged for that commit; it does not automatically copy or migrate all data from the previous commit. The instance a commit tracks under a key is the data set with that key it records, none when the commit stops tracking the key, or else the one its first parent tracks under the key, so a key once staged stays tracked until a later commit records another data set under it or stops tracking it. `Repository::remove_instance` stages the end of tracking a key, which the next commit records in its `untracked` field. `Repository::add_instance` stages a tree, table or graph instance under a key after validating it against the schema it is bound to, and refuses it with the validation report of every failing record; `Repository::committed_instance` reads a tracked instance back and says whether it is stale, recorded against a schema other than the commit's. `Repository::diff_data` lists the keys two commits track differently, each changed key with its shape's delta (the table or graph differ of the edit algebra, or for trees the graph differ of each record's graph form), which `instance_vc::apply` applies; a key whose data sets conform to two schemas is refused until one is migrated. Amend preserves existing data identifiers unless the caller stages replacements. A schema change made through either operation thus does not by itself imply that associated data was transformed.

Data migrates along a stored migration. `data_mig::migrate_forward` reads the `Migration` object it is given, compiles its mapping between its two schemas into a lens, and puts the data set through that shape's get: each tree of a sequence of trees through the tree lens, a table through the table lens and a graph through the graph lens. `data_mig::migrate_backward` puts the migrated data set back against a stored complement, along the migration the complement names. Two conventions bind these objects. A `ComplementObject` records as its `migration_id` the stored migration that produced it and as its `data_id` the data set it was computed from; a complement whose two fields are equal, as repositories written by 0.78 hold, is the complement of that data set under no known migration, and backward migration refuses it with `MigrationConflict::UnknownMigration`, naming the data set to migrate again. A migrated `DataSetObject` records as its `schema_id` the schema tree of its schema, the object `tree::store_schema_as_tree` stores; a `schema_id` naming a `FlatSchema`, as data migrated by 0.78 does, is read through that object. Two identifiers name the same schema when the schemas they hold hash alike (`data_mig::schema_identity`), and staleness, `Repository::committed_instance` and `Repository::diff_data` compare schemas that way.

## Related work

The categorical account of patches and merge also includes homotopical patch theory [@angiuli2014homotopical] and Darcs [@roundy2005darcs]. Work on schema evolution includes the PRISM workbench and its schema-modification operators [@curinomoonzaniolo2008graceful]. panproto combines these ideas with content-addressed storage for protocols, schemas, data, migrations, and complements. [Related work](./related-work.md#schema-versioning-as-structured-merge) gives the broader comparison.
