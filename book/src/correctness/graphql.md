# GraphQL

A [GraphQL](https://spec.graphql.org/September2025/) type system document states what a GraphQL service offers: the object types a query walks through, the interfaces and unions that group them, the enums and scalars at the leaves, the input objects that arguments accept, and the directives that annotate all of them. Reading such a document into panproto is what lets a migration or a lens be written against a service's types, and every definition the reader keeps or refuses changes what that migration may assume. This page states which documents panproto reads, how a document becomes a schema graph, which rules of the specification the reader checks and which it does not, what the writer prints, and the laws the two satisfy.

## Standard and shapes

The reader follows the September 2025 edition of the [GraphQL specification](https://spec.graphql.org/September2025/) (tag `September2025` of [graphql/graphql-spec](https://github.com/graphql/graphql-spec), commit `89d93ebb`), whose chapter 3 defines the type system and whose chapter 2 defines the text. A document is read through the bundled tree-sitter grammar [bkegley/tree-sitter-graphql](https://github.com/bkegley/tree-sitter-graphql) (MIT, commit `5e66e961`, vendored under `grammars/graphql`), so no part of the text is parsed by hand.

[`read_graphql`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/fn.read_graphql.html) reads one document, and [`read_graphql_bundle`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/fn.read_graphql_bundle.html) a type system split over several documents, whose definitions together make one type system. The reader takes every type system definition and extension of the edition: the schema definition and its extension, scalar, object, interface, union, enum and input object types with their extensions, interfaces implementing interfaces, directive definitions with `repeatable` and their locations, applied directives, descriptions as quoted strings and block strings, default values, and the built-in directives `@deprecated`, `@specifiedBy` and `@oneOf`. An extension applies to the definition of its type wherever that definition is, in the order the extensions are read. Without a schema definition the root operation types are the types named `Query`, `Mutation` and `Subscription`, as the specification's default root type names state.

A document holding an executable definition, an operation or a fragment, is refused with [`GraphQlErrorKind::Executable`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/enum.GraphQlErrorKind.html), since a type system document states types and not requests. The issue that brought the format in leaves out any resolution that treats an interface as a supertype of its implementations, and the reader follows it: an `implements` declaration is an edge, the reader checks the specification's implementation rules on it, and no field, argument or directive is inherited through it.

## The GraphQL graph

Every vertex is a schema element, and its id is the element's schema coordinate, the name the specification's section 2.14 gives each element. A named type is a vertex whose kind is its kind (`scalar`, `object`, `interface`, `union`, `enum` or `input-object`) and whose id is its name; a field is a `field` vertex `Type.field`, an argument an `argument` vertex `Type.field(arg:)` or `@directive(arg:)`, an input field an `input-field` vertex `Input.field`, an enum value an `enum-value` vertex `Enum.VALUE`, and a directive definition a `directive` vertex `@directive`. The schema itself is the `schema` vertex `{schema}`, an id no coordinate takes. A built-in scalar the document references is a `scalar` vertex marked `built-in`, since the specification omits built-in scalars from a document.

The edges, listed in [`EDGES`](https://docs.rs/panproto-protocols/latest/panproto_protocols/api/graphql/constant.EDGES.html), join the schema to each root operation type (`root`, named by the operation type), a type to its fields (`field`), values (`value`), input fields (`input-field`), union members (`member`) and the interfaces it declares (`implements`), a field or directive to its arguments (`argument`), and a field, argument or input field to the named type under its wrappers (`type`). Edges keep the order of the document: a type's fields, a union's members and an enum's values are in the order written, with an extension's after the definition's. The edges into a vertex are in the order of their sources' ids, so the order of the definitions is no part of the schema: documents that differ only in it read as the same schema.

Everything else a definition states is a constraint, of the sorts in [`SORTS`](https://docs.rs/panproto-protocols/latest/panproto_protocols/api/graphql/constant.SORTS.html): `description` holds a description's value after the block string rules; `type` holds a type reference as written with its list and non-null wrappers, such as `[Pet!]!`; `default` holds a default value as canonical GraphQL text; `directive` holds one applied directive other than the built-in ones as canonical text, one constraint per application in the order applied; `deprecated` holds the deprecation reason, `No longer supported` when none is given; `specified-by` holds a scalar's specification URL; `one-of`, `repeatable` and `built-in` mark an input object, a directive definition and a scalar; and `location` holds one location of a directive definition, in the order listed. Every sort describes the type system and constrains no instance.

## What the reader refuses

The reader refuses with a [`GraphQlError`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/struct.GraphQlError.html) carrying the index of the document at fault, the schema coordinate of the definition at fault (empty while no definition is read), the byte offset of the text at fault, and what is wrong. The checks run in this order, and the first that fails is the refusal.

1. Each document in order: its encoding (`Encoding`), its syntax as the grammar parses it (`Syntax`, or `NotRead` for a construct the grammar does not parse), and then, definition by definition, executable definitions (`Executable`), names that start with `__` (`ReservedName`), a quoted string holding a line terminator (`LineTerminatorInString`), an enum value named `true`, `false` or `null` (`EnumValueName`), a variable in a constant value (`Variable`), an extension that adds nothing (`EmptyExtension`), and values or types nested deeper than [`MAX_NESTING`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/constant.MAX_NESTING.html) levels (`Nesting`).
2. The names: a type with a built-in scalar's name (`BuiltInTypeName`) or another type's name (`DuplicateType`), a directive with another directive's name (`DuplicateDirective`), a definition of a built-in directive that is not the specification's (`BuiltInDirectiveRedefined`), and a second schema definition (`SchemaDefinitions`).
3. The extensions in the order read: an extension of a type that is not defined (`ExtensionUndefined`) or of another kind (`ExtensionKind`), an extension of a built-in scalar (`NotRead`), `@oneOf` given by an input object extension (`OneOfOnExtension`), an interface, field, member, value or input field already present (`DuplicateInterface`, `DuplicateField`, `DuplicateMember`, `DuplicateValue`), and a schema extension without a schema definition (`SchemaUndefined`).
4. Every type reference names a defined type (`UnknownType`).
5. The root operation types: an operation type given twice (`DuplicateOperation`), a root type that is not an object type (`RootNotObject`), two operation types with one root type (`RootsNotDistinct`), and no `query` root (`QueryRootMissing`).
6. Each type in the order defined, by the rules the specification lists for its kind: no fields, members or values (`NoFields`, `NoMembers`, `NoValues`), names repeated (`DuplicateField`, `DuplicateArgument`, `DuplicateMember`, `DuplicateValue`), a field that does not return an output type (`NotOutputType`), an argument or input field that does not accept an input type (`NotInputType`), `@deprecated` on a required argument or input field (`DeprecatedRequired`), an interface named twice (`DuplicateInterface`), an interface implementing itself (`ImplementsSelf`), an implemented type that is not an interface (`ImplementsNonInterface`), the specification's `IsValidImplementation` (`TransitiveInterface`, `MissingInterfaceField`, `MissingInterfaceArgument`, `ArgumentNotInvariant`, `ExtraArgumentRequired`, `FieldNotCovariant`, `DeprecationNotInherited`), a member that is not an object type (`MemberNotObject`), a OneOf Input Object field that is non-null or has a default value (`OneOfNonNull`, `OneOfDefault`), and an input object that reaches itself through non-null singular fields (`InputCycle`).
7. Each directive definition: its arguments by the rules above, and a definition that references itself directly or through the types and directives it references (`DirectiveSelfReference`).
8. Every applied directive, on the schema, each type and its parts, and each directive definition's arguments: a directive that is not defined (`DirectiveUndefined`), applied where its definition does not list (`DirectiveLocation`), a non-repeatable directive applied twice to one definition with its extensions (`DirectiveRepeated`), an argument the directive does not define (`ArgumentUndefined`) or given twice (`ArgumentRepeated`), a required argument missing or `null` (`ArgumentMissing`), and an argument value that does not coerce to its type (`ValueNotCoercible`).
9. Every default value coerces to its type (`ValueNotCoercible`), and no input object's default values form a cycle as `InputObjectDefaultValueHasCycle` states (`DefaultValueCycle`).

A value coerces by the input coercion rules of chapter 3: `null` to a nullable type only, a list item by item and any other value to a list as a list of one item, `Int` an integer in the 32-bit range, `Float` an integer or a float that is finite in 64 bits, `String` a string, `Boolean` a boolean, `ID` a string or an integer, an enum one of its values, and an input object an object value whose fields are unique and defined, whose required fields are present and not `null`, and which, for a OneOf Input Object, holds exactly one field that is not `null`.

The grammar parses most of the edition, and four constructs it does not are refused by name with [`NotRead`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/enum.NotRead.html): an escape sequence in a string (`StringEscape`, which covers `\"""` in a block string), a quote just before the closing `"""` of a block string (`BlockStringQuote`), a schema extension other than `extend schema` with one operation type in braces (`SchemaExtension`), and, by the reader's choice, an extension of a built-in scalar (`BuiltInScalarExtension`), since the canonical text omits built-in scalars and so could not state it. Each was confirmed by running the grammar on it. A failure of the grammar that is none of these is `Syntax`.

### What the reader does not check

These rules are not checked, and the document is read as written: that a custom scalar's literal is one the scalar accepts, since the specification leaves a custom scalar's coercion to the service; that a scalar specification URL is a URL, and that it links to a specification; that a description is CommonMark; that a definition precedes its extension in the document, since an extension applies wherever its type is defined; that a directive definition lists each location once. The SHOULD rules are not checked either: that types and fields have descriptions, that names follow the recommended casing, that a custom directive's name is prefixed.

## Canonical output

[`write_graphql`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/fn.write_graphql.html) writes a `graphql` schema as its canonical text: the schema definition, always written out with its root operation types in the order of its edges, then each directive definition and then each type definition in the order of their names, built-in scalars left out. A definition's description comes before it on its own line. A field, value, argument and input field are in the order of the edges, and a definition's applied directives follow it, the custom ones in the order read and then `@deprecated`, `@specifiedBy` and `@oneOf`. A string is written quoted when it holds no quote, backslash or line break, and otherwise as the first of three block strings whose value it is ([`string_text`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/fn.string_text.html)): the text between two line breaks, the text alone, or the text followed by a line break. The writer refuses, with a [`GraphQlWriteError`](https://docs.rs/panproto-io/latest/panproto_io/api/graphql/enum.GraphQlWriteError.html), a schema with no schema vertex, a vertex or edge with no place in a document, and a string none of the forms states, such as one holding `"""`. The reader claims no format preservation: comments, layout, the order of definitions and the split into extensions are not kept.

## Conformance corpus

The corpus under `crates/panproto-io/tests/fixtures/conformance/graphql` holds, from [graphql/graphql-js](https://github.com/graphql/graphql-js) (MIT; `UPSTREAM.md` names the commit), the two type system documents of its test utilities, `kitchenSinkSDL` and `viralSDL`, and reads the repository's `fixtures/graphql/swapi.graphql` (BSD-3-Clause) beside them. It adds 58 refusal cases written for panproto from the September 2025 edition, one per rule or construct not read. Every upstream document must read, write its canonical text and read back from it as the same schema, unless `MANIFEST` lists it with the refusal it draws; every case `MANIFEST` lists must be refused at its schema coordinate with its class (`conformance_graphql.rs`). The kitchen sink document is listed: it uses constructs of later drafts, the location `DIRECTIVE_DEFINITION` and `extend directive`, which the September 2025 grammar does not have.

## A document reads as the page defines it {#L-graphql-1}

### Statement

For a document $d$ of the bounded scope, write $R(d)$ for `read` of $d$ and $T(d)$ for the GraphQL text `render(d)`. When $R(d)$ is a reading, `read_graphql` reads $T(d)$ as a schema with exactly the vertices and kinds of $R(d)$, the out-edges of each vertex in the same order with the same kinds, targets and names, and the same constraints in the same order with the same values. When $R(d)$ refuses at schema coordinate $p$ with rule $k$, `read_graphql` refuses at $p$ with rule $k$.

### Outside the domain

The reference reads its own syntax tree of definitions, so text the grammar does not parse, escape sequences, comments, executable definitions, bundles of several documents and deep nesting are checked by the fixed tests of `graphql_reads_september_2025.rs` and the corpus. A refusal's byte offset, its document index and its message are not compared; the schema coordinate and the rule are.

### Definitions used

$R$ applies the checks of the refusal section in their order, with its own model of the type system and its own coercion and implementation rules. The scope is a base type system: a `Query` type with `node(id: ID!): Node` and `search(filter: Filter): [Result]`, an interface `Node { id: ID! }`, an object type `Pet` with `id` and `name`, a union `Result`, an enum `Kind { CAT DOG }`, an input object `Filter { text: String kind: Kind }` and a directive `@tag(name: String!)` on objects and fields. The scope varies nine choices on it: a field added to `Pet` (4: none, an `owner` field with a defaulted, deprecated argument, `@tag` and a deprecation reason holding quotes, and two that break a rule: a name starting with `__`, a field returning `Filter`), what `Pet` implements (3: `Node`, and two that break a rule: `Node` with an `id` of type `ID`, the object type `Query`), the member of `Result` (2: `Pet`, and the interface `Node`), the default of `search`'s argument (4: none, `{text: "a"}`, `{kind: CAT}`, and `{kind: BIRD}`), the directives on `Pet` (4: none, `@tag(name: "x")`, and two that break a rule: `@tag` without its argument, `@deprecated`), one extension (4: none, a field `legs` of `Pet`, a value `FISH` of `Kind`, and an object extension of the enum `Kind`), the schema definition (4: none, `query` only, a described one with `Pet` as mutation root, and one whose `query` root is the union `Result`), the descriptions (2: none, a quoted one on `Query` and a block one on `Pet.name`), and the form of `Filter` (3: plain, `@oneOf`, and one with a field `self: Filter!`). That is $4 \cdot 3 \cdot 2 \cdot 4 \cdot 4 \cdot 4 \cdot 4 \cdot 2 \cdot 3 = 36864$ documents. The rules the scope leaves out are each a case of the conformance corpus and of the fixed tests.

### Proof

1. Production reads $T(d)$ through the grammar, which parses every construct `render` writes (keywords, names, quoted strings without escapes, block strings, lists, input objects, wrappers and directives) into the tree whose definitions are those of $d$, in order.
2. Production checks the same conditions as $R$ in the same order: the per-definition checks in document order, then the names, the extensions, the type references, the roots, the types in the order defined, the directive definitions, the applied directives and the default values, each in the order the refusal section lists, with the same coordinates. The coercion rules, `IsValidImplementation`, `IsValidImplementationFieldType`, `IsSubType`, the input cycle search in field order and `InputObjectDefaultValueHasCycle` are the specification's algorithms in both, so the first condition that fails is the same, at the same coordinate, with the same rule.
3. On a document both accept, both create the same vertices with the same coordinates, add a type's `implements` edges before its `field` edges, a field's `argument` edges before its `type` edge, a union's members and an enum's values and an input object's fields in the order written with an extension's after, and keep each vertex's constraints in the order of the sorts above, an applied directive's text and a value's text formatted the same, so the readings agree.
4. The exhaustive differential checks the agreement on all 36864 documents, of which 432 are accepted: each choice is read on its own in 2 added fields, 1 implementation, 1 member, 3 defaults, 2 directive lists, 3 extensions, 3 schema definitions, 2 description choices and 2 forms of `Filter`, and a read choice of one kind breaks no rule of another, since the base defines every type the read choices name and the defaults coerce under both read forms of `Filter`, so the accepted documents are the $2 \cdot 1 \cdot 1 \cdot 3 \cdot 2 \cdot 3 \cdot 3 \cdot 2 \cdot 2 = 432$ whose nine choices are each read. The property differential checks random choices with a description of `Query` drawn from spaces, tabs, quotes, backslashes, line breaks and letters, which makes the string forms meet the rest of the document.

## The writer prints the canonical document, which reads back as the same schema {#L-graphql-2}

### Statement

For a document $d$ of the bounded scope that $R$ accepts, write $C(d)$ for `canonical_text(d)`. `write_graphql` writes the schema `read_graphql` reads from $T(d)$ as exactly $C(d)$, and `read_graphql` reads $C(d)$ as a schema with the same reading.

### Outside the domain

Schemas that no document reads as (no schema vertex, a field with no `type` constraint, a vertex of a kind with no place in a document, a string none of the forms states) are refused by the writer; the reference, which writes from documents, does not model them.

### Definitions used

$C(d)$ is the text the canonical output section describes, built by the reference from its reading of $d$: the schema definition, the directive definitions and the types in the order of their ids, each part in the order of its edges, each string in the first form whose value it is.

### Proof

1. Production writes each part from the reading of [L-graphql-1](#L-graphql-1): a type reference and a default from their constraints, which are the texts $C$ writes; the custom directives from their constraints in order and the built-in ones from their sorts; each string through the same three forms in the same order. So the written text is $C(d)$.
2. $C(d)$ reads as the same reading: each form of a string is kept only when the block string rules give back its value, so every description, reason and URL reads back unchanged; a definition written once with its extensions folded in gives the edges and constraints in the order they had; the schema definition written out names the roots the reading had, which for an implicit schema are the default root types in the order query, mutation, subscription; and the built-in directives written after the custom ones go back to their own sorts, so the custom directives keep their order.
3. The exhaustive differential checks both equalities on all 432 accepted documents, and the property differential on generated ones.
