# AsyncAPI

An [AsyncAPI](https://www.asyncapi.com/docs/reference/specification/v3.1.0) description states the surface of a message-driven API: the servers an application connects to, the channels it sends to and receives from, the operations it performs on them, the messages those channels carry and the shapes of their payloads and headers. Reading a description into panproto is what lets a migration or a lens be written against the messages an application exchanges, and every field the reader keeps, resolves or refuses changes what that migration may assume. This page states which descriptions panproto reads, how a description becomes a schema graph, how its references resolve, what the reader refuses and what it does not check, what the writer prints, and the laws the two satisfy.

## Standard and shapes

The reader follows major version 3 of the [AsyncAPI Specification](https://www.asyncapi.com/docs/reference/specification/v3.1.0), read against the text of its latest release, 3.1.0 (the file `spec/asyncapi.md` of [asyncapi/spec](https://github.com/asyncapi/spec) at tag `v3.1.0`, commit `b3fac5bb`). It reads a document whose `asyncapi` field is a version string of minor version 3.0 or 3.1: `3.0.` or `3.1.`, a patch number, and optionally `-` and alphanumeric characters, as the specification's Version String section allows. The specification promises that a minor version does not break a reader of the one before, and the 3.1.0 text adds to 3.0.0 only the ROS 2 bindings and wording, so a 3.0 document is read under the 3.1.0 text. Any other version is refused at the `asyncapi` field with `Version`: a 2.x document has another structure (operations are the `publish` and `subscribe` members of a channel, and messages are not keyed), and a later minor version may add fields that a 3.1 reading would drop.

The reader is [`read_asyncapi`](https://docs.rs/panproto-io/latest/panproto_io/api/asyncapi/fn.read_asyncapi.html) for one document and [`read_asyncapi_bundle`](https://docs.rs/panproto-io/latest/panproto_io/api/asyncapi/fn.read_asyncapi_bundle.html) for a description split over several documents, each an AsyncAPI document or a fragment document with an optional retrieval URI, the first the entry document; both are in `panproto-io` (feature `tree-sitter`). A fragment document holds parts of a description (messages, schemas, servers, parameters) at the JSON pointers that references name, with no `asyncapi` field of its own, as the `common` files of the specification's social media example do. The reader parses neither JSON nor YAML itself: a document whose first byte other than whitespace is `{` goes through the shared JSON route ([`read_json`](https://docs.rs/panproto-io/latest/panproto_io/config/tree/fn.read_json.html)), any other through the shared YAML route ([`read_yaml`](https://docs.rs/panproto-io/latest/panproto_io/config/tree/fn.read_yaml.html)), so a repeated key, a YAML alias or a second YAML document is refused before the reader sees the document, as the [text formats](text-formats.md) page states. `panproto-protocols` does not parse AsyncAPI, and its schema dispatches refuse `asyncapi` and name this reader.

The `asyncapi` protocol declares a tree syntactic and a tree semantic shape. The shapes describe an instance of the schema, which is a message's payload or headers: JSON data, which is a tree. The schema graph itself is not a tree, since references add edges between its objects.

| Supported | Read as |
|---|---|
| The AsyncAPI Object and every object it holds: Info, Contact, License, Server, Server Variable, Channel, Operation, Operation Trait, Operation Reply, Operation Reply Address, Parameter, the four Bindings Objects, Message, Message Trait, Message Example, Tag, External Documentation, Components (all nineteen maps), Multi Format Schema, Security Scheme (all thirteen types), OAuth Flows, OAuth Flow, Correlation ID | A vertex per object, whose kind names the object (`asyncapi`, `info`, `contact`, `license`, `server`, `server-variable`, `channel`, `operation`, `operation-trait`, `operation-reply`, `operation-reply-address`, `parameter`, `server-bindings`, `channel-bindings`, `operation-bindings`, `message-bindings`, `message`, `message-trait`, `message-example`, `tag`, `external-docs`, `components`, `multi-format-schema`, `security-scheme`, `oauth-flows`, `oauth-flow`, `correlation-id`) |
| A field holding an object, a list of objects or a map of objects (the Servers, Channels, Operations, Messages and Parameters Objects are maps) | An edge per object (the field's name in kebab case: `info`, `servers`, `channels`, `messages`, `traits`, `correlation-id`, `security-schemes` and the rest), named by its index or key |
| A field holding a string, `null`, any value, a list of strings or a map of strings (`asyncapi`, `title`, `host`, `address`, `action`, `location`, `availableScopes` and the rest) | A constraint of the field's name holding the value as canonical JSON text |
| A binding: the value of one protocol's field of a Bindings Object (`http`, `kafka`, `mqtt` and the other seventeen) | A constraint of the protocol's name holding the binding as canonical JSON text |
| An empty map or list of objects | A constraint of the field's name holding `{}` or `[]`, so an operation's `messages: []` (no messages) stays distinct from an absent `messages` (every message of the channel) |
| A Reference Object | A `reference` vertex with a `ref` edge to the object it resolves to, named by the reference as written; any other member, which the specification ignores, an `ignored` constraint holding the member |
| A Schema Object (a message's `headers` or `payload`, a value of `components/schemas`) | The [JSON Schema](json-schema.md) reading of its subschemas, as draft-07 with the AsyncAPI vocabulary, whose `discriminator`, `externalDocs` and `deprecated` are kept constraints, and with `definitions` reached by `definition` edges |
| A Multi Format Schema Object whose `schemaFormat` is the AsyncAPI Schema Object (`application/vnd.aai.asyncapi`, its `+json` or `+yaml` form, with a 3.0 or 3.1 `version`) or JSON Schema draft-07 (`application/schema+json;version=draft-07` or its `+yaml` form) | A `multi-format-schema` vertex with a `schemaFormat` constraint and a `schema` edge to its Schema Object, read as draft-07, with the AsyncAPI vocabulary for the first format and without it for the second |
| A specification extension (`x-`) | An `extension` constraint holding the member as written |

| Not supported | Refusal | Reason |
|---|---|---|
| An `asyncapi` version other than 3.0.x and 3.1.x, 2.6.0 among them | `Version` | Another document structure, or fields a 3.1 reading would drop |
| A Multi Format Schema Object of any other format: Avro, the OpenAPI 3.0 Schema Object, RAML data types, Protocol Buffers, a custom format | `SchemaFormat` | Each is another schema language; the reader reads none of them into the draft-07 subschemas of this protocol |
| In a Schema Object: `$schema`, `$id`, `dependencies`, `additionalItems`, `items` as an array, a 2020-12 keyword draft-07 does not define (`$defs`, `prefixItems`, `$anchor` and the rest, and `deprecated` outside the AsyncAPI vocabulary), a member beside `$ref` | `Schema` with `Draft07` | A `$ref` follows the Reference Object, so it resolves against the document whatever `$id` says and its siblings are ignored, which the reader refuses to drop silently; `dependencies` and the tuple form of `items` mix subschemas with other values; the 2020-12 keywords are unknown keywords in draft-07, which 2020-12 would read as applicators |
| A reference to a document outside the bundle | `External` | The reader performs no network access; the referenced document must be given in the bundle with its retrieval URI |

Traits are read as edges to the trait objects and are not merged into the operation or message they apply to, so a reading keeps the description as written; the specification's merge (JSON Merge Patch, the target's own fields winning) is a function of what the reader keeps. A binding is kept as its JSON text and not read against the binding's own specification in [asyncapi/bindings](https://github.com/asyncapi/bindings), so a Schema Object or a reference inside a binding is kept as written and not resolved.

## The AsyncAPI graph

Each object of a document is a vertex whose id is the document's prefix, then `#`, then the object's JSON pointer from the document root (RFC 6901, `~` written `~0` and `/` written `~1`): the prefix is the document's retrieval URI when it has one, else empty, so the root of a lone document is `#` and the message `UserSignedUp` of the channel `user/signedup` (a key with a slash) is `#/channels/user~1signedup/messages/UserSignedUp`. A Schema Object is a subschema vertex named the same way, so the subschemas of every Schema Object of a description are vertices of the one schema. The protocol's object table ([`OBJECTS`](https://docs.rs/panproto-protocols/latest/panproto_protocols/api/asyncapi/constant.OBJECTS.html)) lists each kind's fields in the order of the specification's tables, and the reader visits them in that order, so an object's constraints and edges come in that order whatever the order of the source. The one exception is the edges of a field that holds schemas (a message's and a trait's `headers`, a message's `payload`, `components/schemas`, a Multi Format Schema Object's `schema`): they are added after the Schema Objects are built, in the order met, so they follow the object's other edges and a map of schemas keeps its order whether each entry is a Schema Object, a Multi Format Schema Object or a Reference Object.

Every value is kept, never interpreted away: a value field is a constraint whose value is canonical JSON text (no whitespace, members in source order, integers and exact decimals as written in their canonical form, a float in its shortest round-tripping form). The `asyncapi` field is a constraint like any other, so the version read is the version written. The root of each AsyncAPI document is an entry of the schema, and every `definitions` member of a Schema Object is an entry, as every `$defs` member is on the JSON Schema page.

## How references resolve

A Reference Object's `$ref` is a JSON Reference: the reader resolves it against its document's base URI, the retrieval URI or none, with the RFC 3986 functions of the shared reference resolution ([`resolve_uri_reference`](https://docs.rs/panproto-io/latest/panproto_io/resolution/fn.resolve_uri_reference.html) and [`resolve_uri_against`](https://docs.rs/panproto-io/latest/panproto_io/resolution/fn.resolve_uri_against.html)). A reference that is only a fragment names a place of its own document. Any other reference is resolved and split at `#`: the part before must be the retrieval URI of a document of the bundle (`External` otherwise), and the fragment must be empty or a JSON pointer, percent-decoded (`RefTarget` otherwise). In an AsyncAPI document, the place it names must be an object the reader read (`RefTarget`). In a fragment document, a place that no reference has named before is read when a reference first names it, as the kind of object the reference's place takes, and every reference that place holds joins the references to resolve; a pointer that names nothing in the fragment is refused with `RefTarget`. The object named must be of the kind the reference's place takes (`RefKind`): a channel's message reference must name a message, an operation's channel reference a channel, a schema place's reference a Schema Object or a Multi Format Schema Object. A Reference Object may name another Reference Object of the same kind, and a chain of references that returns to a place it has visited is refused with `RefCycle`.

A Schema Object's format is the AsyncAPI Schema Object unless a Multi Format Schema Object names another, and the specification requires a reference made in a schema to name a schema of the same format. A Reference Object at a schema place (a message's `headers` or `payload`, a value of `components/schemas`) is in the AsyncAPI format, so it must not name a draft-07 Multi Format Schema Object (`FormatMismatch`). A `$ref` inside a Schema Object is read by the JSON Schema reader as a JSON Reference too: against the document, never against a `$id`, which the reader refuses. It must name a subschema of a Schema Object the description holds (`Schema` with `RefTarget` otherwise); when it names a place of a fragment document that no Schema Object holds, the node there is read as a further Schema Object of the referring one's vocabulary, after the Schema Objects before it.

## What the reader refuses

Every refusal is an [`AsyncApiError`](https://docs.rs/panproto-io/latest/panproto_io/api/asyncapi/struct.AsyncApiError.html) carrying the index of the document, the JSON pointer of the value at fault, its byte offset, and an [`AsyncApiErrorKind`](https://docs.rs/panproto-io/latest/panproto_io/api/asyncapi/enum.AsyncApiErrorKind.html), and the reader returns the first fault in this order. First, each document's route refusal (`Syntax`), and each retrieval URI absolute with no fragment (`Invalid`) and given once (`DuplicateDocument`), and the entry document an AsyncAPI document (`Invalid`); then, AsyncAPI document by AsyncAPI document, the root an object (`WrongType`), `asyncapi` present (`NotAsyncApi`), a string (`WrongType`) and a 3.0 or 3.1 version (`Version`).

Then the reader walks the objects depth first. At each object it checks, in this order: that a place read before as one kind is not read again as another (`Invalid`, which only a fragment document can meet); that it is an object (`WrongType`); each member in source order, which must be a field of the object (`UnknownField`) or an extension whose name matches `^x-[\w\d\.\x2d_]+$` (`Name`); each REQUIRED field in table order (`Missing`); the object's own rules; and then each field in table order, its value's JSON kind (`WrongType`) before the objects it holds. A field that holds only Reference Objects (an operation's and a reply's `channel`, a channel's `servers`, an operation's and a reply's `messages`) holding anything else is refused with `Invalid`. A key of the Servers Object or of a channel's Parameters Object must match `^[A-Za-z0-9_\-]+$`, and a key of a Components map `^[a-zA-Z0-9\.\-_]+$` (`Name`). The objects' own rules are the MUSTs of the 3.1.0 text that the field table does not state:

- a field that holds an absolute URL (`termsOfService`, a Contact's, License's and External Documentation's `url`, `openIdConnectUrl`, an OAuth flow's three URLs) or a URI (the root `id`) begins with a scheme (`Invalid`);
- `defaultContentType` and a Message's and Message Trait's `contentType` are specific media types: a type and a subtype, each an RFC 6838 restricted name (`Invalid`);
- a channel's address has no query or fragment (`Invalid`), its expressions are names enclosed in braces (`Template`), its `parameters` is present only when the address holds an expression (`Invalid`), holds a parameter for every expression (`MissingParameter`) and none for anything else (`UnknownParameter`);
- an operation's `action` is `send` or `receive` (`Invalid`);
- the `location` of a Parameter, a Correlation ID and an Operation Reply Address is a runtime expression: `$message.header` or `$message.payload`, optionally followed by `#` and a JSON pointer (`Invalid`);
- a Message Example has `headers` or `payload` (`Missing`);
- a Multi Format Schema Object's `schemaFormat` is one of the formats above (`SchemaFormat`);
- a Security Scheme's `type` is one of the thirteen, it has the fields its type requires and none another type uses (`Missing`, `Invalid`), an API key is in `user` or `password` and an HTTP API key in `query`, `header` or `cookie`, and `bearerFormat` is used only with the `bearer` scheme (`Invalid`); each OAuth flow has its URLs and none another flow uses (`Missing`, `Invalid`).

After the walk come, in this order: the references, in the order they were read, each place of a fragment document read when first named; the Schema Objects, by the JSON Schema reader, whose refusals are `Schema` carrying the JSON Schema kind; and then, object by object in the order read, the rules that join objects. A channel of the root Channels Object names servers of the root Servers Object of its document (`Placement`). An operation of the root Operations Object, and the reply inside one, name a channel of the root Channels Object (`Placement`). A reply with an `address` names a channel whose `address` is `null` or absent (`Invalid`). Each message an operation or a reply names is a message of the channel it names: the reference names a member of that channel's `messages` (`NotInChannel`).

### What the reader does not check

These MUSTs of the specification are not checked, and the description is read as written: that a URL or URI is well formed beyond its scheme, and that an absolute URL has no fragment as RFC 3986 section 4.3 would require; that an email address has the form of one; the parameters of a media type after its `;`; that a reply's messages are messages of the operation's channel when the reply names no channel of its own; that a message's `headers` schema describes an object, and that it does not describe protocol headers; that a Schema Object's `discriminator` names a property it declares and requires; that a `default` conforms to the type of its Schema Object; that a `$ref` inside a draft-07 Multi Format Schema Object names a schema of the same format; that the object which traits merge into is a valid object; that a binding holds protocol-specific information only and follows its binding specification; that a message example validates against the message's schemas; that a runtime expression's JSON pointer names a place of a message; that every object outside the components is used by the application. None of the SHOULD rules is checked: that a `pattern` is an ECMA 262 regular expression, that identifiers follow programming naming conventions.

## Canonical output

[`write_asyncapi`](https://docs.rs/panproto-io/latest/panproto_io/api/asyncapi/fn.write_asyncapi.html) writes the document of an `asyncapi` schema rooted at a given vertex as its canonical text: one line of JSON with no whitespace between tokens, ended by a line feed. An object's members are its fields in the order of the object table, which is the order of the specification's tables, each value field from its constraint, each field of objects from its edges in the order of the edges, an empty map or list from its constraint; then its extensions in the order read. A Reference Object is its `$ref` and then its ignored members in the order read. A Schema Object is written as the JSON Schema page's writer writes a subschema, with `definitions` after the 2020-12 applicators. The writer refuses, with an [`AsyncApiWriteError`](https://docs.rs/panproto-io/latest/panproto_io/api/asyncapi/enum.AsyncApiWriteError.html), a root or target that is not a vertex, a constraint that is not JSON text of its form, and a vertex or edge that has no place in a document. The reader claims no format preservation: YAML is written as JSON, and the layout and member order of the source outside the order above are not kept. Only the entry document is written; a fragment document's places that the description reads stay where they are, and the canonical text names them by the same references.

## Conformance corpus

The corpus under `crates/panproto-io/tests/fixtures/conformance/asyncapi` holds, from [asyncapi/spec](https://github.com/asyncapi/spec) (Apache License 2.0, with its `NOTICE`; `UPSTREAM.md` names the commit), the 28 example documents of the 3.1.0 release at commit `b3fac5bb`: 19 single documents and the social media example, whose five services are read as bundles with its four `common` files as fragment documents, under their paths as retrieval URIs. It adds 57 refusal cases written for panproto from the 3.1.0 text, each breaking one rule. Every upstream entry document must read, write its canonical text and read back from it as the same schema, unless `MANIFEST` lists it with the refusal it draws; every case `MANIFEST` lists must be refused at its pointer with its class (`conformance_asyncapi.rs`). One upstream document is a declared limit in `asyncapi-limits.txt`, which the test checks: its message payloads are Avro schemas.

## A document reads as the page defines it {#L-asyncapi-1}

### Statement

For a document $d$ of the bounded scope, write $R(d)$ for `read` of $d$ as the one AsyncAPI document of a description, with no retrieval URI, and $T(d)$ for the JSON text `render(d)`. When $R(d)$ is a reading, `read_asyncapi` reads $T(d)$ as a schema with exactly the vertices and kinds of $R(d)$, the out-edges of each vertex in the same order with the same kinds, targets and names, the same constraints in the same order with the same JSON texts, the same required edges, the same entries in the same order and the same root. When $R(d)$ refuses at pointer $p$ with class $k$, `read_asyncapi` refuses at $p$ with class $k$.

### Outside the domain

The reference reads data trees of nulls, booleans, integers and strings, so floats, exact decimals, wide integers and YAML are checked by the fixed tests and the corpus, as are bundles of several documents with fragment documents. A refusal's byte offset and its message are not compared; the document, pointer and class are. Refusals of the JSON route are the route's subject.

### Definitions used

$R$ applies the rules of the sections above in their order, with its own field table, and reads Schema Objects with `read_draft07`, the JSON Schema reference's reading of draft-07 Schema Objects held at JSON pointers of AsyncAPI documents (each document a resource, a `$ref` resolved against the document, the AsyncAPI vocabulary kept and checked where it is in effect). The scope is a base document holding a server `s`, a channel `c` with the address `c/{id}`, its parameter and a message `m` referring to the component message `M`, a channel `r` with a `null` address, and components holding a Schema Object `S` (a property `n/m`, required, and a `discriminator`), a draft-07 Multi Format Schema Object `F`, a server `z`, a channel `C`, an operation `P` on `C`, an HTTP API key scheme `key`, an operation trait `t`, a message trait `MT` and message bindings `B`. The scope varies five choices on it: the `asyncapi` version (4: `3.1.0`, `3.0.0`, and two refused, `2.6.0` and `3.2.0`), a second channel `d` (6: one with a server reference, bindings and an extension, a Reference Object to `C` with an ignored member, one whose message's payload is an array of `S`, and three that break a rule: an address with a query, a parameter for no expression, a server of the components), the operation `o` (6: a `receive` with a message of `c` and a reply on `r`, a `send` with a trait, bindings and no messages, a Reference Object to `P`, and three that break a rule: the action `publish`, a channel of the components, a message of the components), the message `M` (7: a payload referring to `S` with a content type and a correlation ID, inline headers and a payload with `definitions` and a `$ref` into them and an example, an AsyncAPI-format Multi Format Schema Object with a trait, a `true` payload with a bindings reference, and three that break a rule: an Avro payload, a payload referring to `F`, a payload with `$id`), and a member added to the document (5: none, an extension, `defaultContentType`, and two that break a rule: `paths` and a relative `id`). That is $4 \cdot 6 \cdot 6 \cdot 7 \cdot 5 = 5040$ documents. The rules the scope leaves out (an inline channel, a message reference to a schema, an empty message example, an extension name, and the rest) are each a case of the conformance corpus.

### Proof

1. Production reads $T(d)$ through the JSON route, which reads a JSON text of objects, arrays, strings, integers, booleans and nulls as the tree $d$, members in source order (the route's grammar and its refusals are the shared JSON route's).
2. Production checks the same conditions as $R$ in the same order: the version of the root; then, at each object of the depth-first walk in table order, its kind, its members in source order, its REQUIRED fields in table order, its own rules in the order the section on refusals lists them, and its fields' JSON kinds before the objects they hold; then the references in the order read; then the Schema Objects by the draft-07 rules above, which `read_draft07` follows with the checks of the JSON Schema page for every keyword draft-07 shares with 2020-12 (whose agreement [L-json-schema-1](json-schema.md#L-json-schema-1) states for `read`); then the joins, object by object in the order read. Both locate a reference by the same RFC 3986 resolution and the same JSON pointer decoding, so the first condition that fails is the same, at the same pointer, with the same class.
3. On a document both accept, both create the same vertices with the same ids (the same pointer escaping), add each edge of a field that holds objects when its target is read, in table order, keep each value in table order with the extensions after it, add the Schema Objects' vertices and edges after the references, then the edges of the fields that hold schemas in the order they were met, then each Reference Object's edge in the order resolved, so the readings agree.
4. The exhaustive differential checks the agreement on all 5040 documents, of which 216 are accepted: each choice is read on its own in 2 versions, 3 channels, 3 operations, 4 messages and 3 added members, and a read choice of one kind breaks no rule of another, since the base declares every object the read choices refer to and each read choice touches a different place of the document, so the accepted documents are the $2 \cdot 3 \cdot 3 \cdot 4 \cdot 3 = 216$ whose five choices are each read. The property differential checks documents with up to three further channels, each one of the 6 channel forms under a key drawn from `e`, `f/g`, `h~i` and `j`, which makes the escaping of keys and the root channel rules meet each other.

## The writer prints the canonical document, which reads back as the same schema {#L-asyncapi-2}

### Statement

For a document $d$ of the bounded scope that $R$ accepts, write $C(d)$ for `canonical_text(d)`. `write_asyncapi` writes the schema `read_asyncapi` reads from $T(d)$, at its root, as exactly $C(d)$, and `read_asyncapi` reads $C(d)$ as a schema with the same reading.

### Outside the domain

Schemas that no document reads as (a missing root, a constraint that is not JSON, a vertex of a kind with no place in a document, a Reference Object without exactly one edge) are refused by the writer; the reference, which writes from documents, does not model them.

### Definitions used

$C(d)$ is the compact JSON of $d$ in which each object's members are reordered as the canonical-output section states and each Schema Object is written as `canonical_text` of the JSON Schema page writes it, followed by a line feed.

### Proof

1. Production writes each value field from its constraint's JSON text, which by [L-asyncapi-1](#L-asyncapi-1) is the compact JSON of the field's value in $d$; each reference from its edge's name, which is the reference as written; each field of objects from its edges, which are in the order of the field's entries in the source; each Schema Object by the JSON Schema writer, which by [L-json-schema-2](json-schema.md#L-json-schema-2) writes the canonical subschema, `definitions` included as the last applicator; and it orders an object's groups as $C$ does.
2. $C(d)$ is a JSON text, so the JSON route reads it as the tree of $d$ with each object's members reordered. An accepted reading depends on an object's member order only through the order of its extensions, of a Reference Object's ignored members and of each map's and list's entries, which $C$ keeps: the reader visits fields in table order whatever their order in the source, and refusals do not arise since $d$ is accepted and every rule is a condition on members, not on their order. The reading of $C(d)$ is therefore the reading of $d$.
3. The exhaustive differential checks both equalities on all 216 accepted documents, and the property differential on generated ones.
